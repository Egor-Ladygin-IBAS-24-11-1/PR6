# ПР №6. Анализ сетевого трафика: tcpdump и Wireshark

**Цель:** Освоить базовые методы захвата и анализа сетевого трафика с помощью `tcpdump`, `tshark` и `Wireshark`. На практике убедиться в опасности передачи данных по открытому HTTP и понять границы защиты, которую даёт HTTPS.

**Используемое окружение:**
- ОС: Debian 12 (виртуальная машина)
- Интерфейс для захвата: `lo` (loopback) для тестов, `enp0s3` для реального трафика
- Сервер: `python3 -m http.server 8080`

## 1. Разбор строки tcpdump

В ходе базового захвата трафика была получена строка, отражающая попытку установки соединения (рукопожатие TCP). Разберём её детально.

**Исходная строка:**
`12:34:56.789012 IP 127.0.0.1.44321 > 127.0.0.1.8080: Flags [S], seq 2994331821, length 0`

| Поле | Значение | Что означает |
|------|----------|--------------|
| `12:34:56.789012` | Временная метка | Точное время захвата пакета с точностью до микросекунд. |
| `IP` | Тип протокола | Указывает, что использовался протокол сетевого уровня IPv4. |
| `127.0.0.1.44321` | Адрес и порт отправителя | Исходный порт (эфемерный) на localhost, назначенный ОС для данного соединения. |
| `>` | Направление | Поток данных движется от отправителя к получателю. |
| `127.0.0.1.8080` | Адрес и порт получателя | Целевой порт, на котором работает наш HTTP-сервер. |
| `Flags [S]` | Флаг TCP SYN | Первый шаг «трёхстороннего рукопожатия». Клиент запрашивает установку соединения. |
| `seq 2994331821` | Номер последовательности | Начальный серийный номер для синхронизации данных в этом потоке. |
| `length 0` | Длина полезной нагрузки | В SYN-пакете данные не передаются, только заголовки TCP. |

## 2. Перехваченные данные HTTP

Для демонстрации использовался Python HTTP-сервер. С помощью `curl -X POST` были отправлены учётные данные: `admin` и `supersecret123`. Захват вёлся с флагом `-A`.

**Результат перехвата (`tcpdump -i lo -n -A port 8080`):**
В ASCII-выводе пакета чётко видны сырые данные HTTP-запроса:

POST /login HTTP/1.1
Host: localhost:8080
User-Agent: curl/7.88.1
Accept: */*
Content-Type: application/x-www-form-urlencoded
Content-Length: 38

username=admin&password=supersecret123

Что видно в трафике:
Виден полный URL, все HTTP-заголовки и тело запроса с логином и паролем в нешифрованном виде.

Кто в реальной сети может так же прочитать этот трафик:

    Администратор любой промежуточной точки маршрутизации (роутера, шлюза).

    Злоумышленник, реализовавший атаку «Человек посередине» (MITM), например, через ARP-спуфинг в локальной сети.

    Провайдер интернета, фиксирующий проходящий трафик.

    Владелец публичной Wi-Fi точки, запустивший анализатор пакетов на маршрутизаторе.

3. Follow TCP Stream

При анализе в Wireshark была применена функция Follow → TCP Stream к POST-запросу.

Что видит злоумышленник, перехвативший этот трафик:
Злоумышленник видит полную сессию взаимодействия клиента и сервера в читаемом текстовом виде (красным — запрос клиента, синим — ответ сервера).
Скомпрометированные данные:

## 4. HTTP vs HTTPS — сравнение

Результаты сравнительного анализа отправки одних и тех же данных на HTTP (порт 8080) и HTTPS (порт 443).

| Что наблюдаем | HTTP (порт 8080) | HTTPS (порт 443) |
|---|---|---|
| IP-адреса сторон | Видны | Видны (без изменений) |
| Порт назначения | Виден (8080) | Виден (443) |
| Заголовки HTTP | Видны полностью (`Host`, `User-Agent` и др.) | Не видны (внутри TLS-туннеля) |
| Тело запроса | Видно открытым текстом (`username=admin&password=...`) | Не видно (шифротекст) |
| Логин и пароль | Видны | Не видны в теле запроса/ответа |
| Имя домена (SNI) | Видно в заголовке `Host:` | Видно в поле SNI на этапе TLS Handshake |

## 5. DNS и приватность

Был выполнен захват DNS-запросов (порт 53) во время подключения к HTTPS-сайтам.

**Команда:** `sudo tcpdump -i enp0s3 -n port 53`

**Какие домены видны в DNS даже при HTTPS:**
- `github.com`
- `example.com`
- `google.com`
Все запросы на разрешение имён передаются в открытом виде по UDP/53.

**Что это означает для приватности:**
HTTPS шифрует содержимое общения, но не скрывает факт посещения конкретного сайта от провайдера или анализатора трафика. Зная IP-адреса или видя DNS-запросы, можно составить цифровой профиль пользователя (историю посещений). DNS over HTTPS (DoH) или DNS over TLS (DoT) призваны решить эту проблему, шифруя и сами запросы на разрешение доменных имён.

## 6. Base64

В одном из перехваченных HTTP-запросов фигурировал заголовок `Authorization: Basic dmFzeWE6TXlQYXNzd29yZDIwMjQ=`. Было проведено декодирование.

**Команда и результат:**
```bash
echo 'dmFzeWE6TXlQYXNzd29yZDIwMjQ=' | base64 -d
# Вывод: vasya:MyPassword2024

# Почему Base64 не является шифрованием:
Base64 — это схема кодирования, а не шифрования. У неё нет криптографического ключа. Её задача — представить бинарные данные в текстовом виде, безопасном для передачи по каналам, рассчитанным на текст. Обратное преобразование (base64 -d) не требует секретов и выполняется мгновенно. 
HTTP Basic Auth с Base64 не защищает пароль, а лишь маскирует его от беглого взгляда.
## 7. tshark vs tcpdump

Сравнение инструментов на основе практического опыта.

| Инструмент | Когда использовать |
|---|---|
| **tcpdump** | Быстрый «наколенный» захват трафика на удалённом сервере без GUI. Минималистичный, идеален для просмотра сырых данных и легковесного мониторинга в реальном времени. |
| **tshark** | Продвинутый анализ на сервере без GUI. Используется, когда нужны дисплейные фильтры Wireshark (`-Y`), детальная статистика (`-z`) или вычленение полей (`-T fields`). |
| **Wireshark** | Глубокое интерактивное изучение трафика на рабочей станции. Незаменим для визуального анализа иерархии протоколов, визуализации TCP-потоков и разбора сложных инцидентов. |

## 8. Каналы утечки через сеть

**Какие меры защиты закрывают сетевой канал утечки:**

1. **Повсеместное использование TLS (HTTPS, FTPS, LDAPS):** Базовый минимум для защиты данных при передаче от пассивного прослушивания.
2. **HSTS (HTTP Strict Transport Security):** Принудительно заставляет браузер всегда использовать HTTPS-версию сайта, исключая возможность атаки «даунгрейда» до HTTP.
3. **DNS over HTTPS (DoH) / DNS over TLS (DoT):** Шифрование DNS-запросов, чтобы скрыть историю посещений от провайдера.
4. **VPN (Virtual Private Network):** Создание зашифрованного туннеля до доверенной точки выхода в сеть, что защищает весь трафик целиком в небезопасных сетях (например, публичный Wi-Fi).

## Выводы

В ходе практической работы были получены и проанализированы данные, наглядно демонстрирующие уязвимости открытых протоколов:

1. **HTTP — это текст:** Работа с `tcpdump -A` доказала, что любая информация, передаваемая по HTTP (логины, пароли, ключи сессий), легко читается без всякой расшифровки. Опора на Base64 как на «защиту» (Basic Auth) абсолютно бесполезна.
2. **HTTPS шифрует содержимое, но не маскирует факт соединения:** Сравнение трафика показало, что TLS скрывает параметры запроса и тело ответа, но IP-адреса и имена доменов (через SNI/DNS) остаются видны.
3. **Инструменты анализа:** `tcpdump` и `tshark` показали себя как мощные средства для работы на сервере, а Wireshark — как незаменимый инструмент для наглядного визуального расследования сетевых инцидентов.
4. **Практическая значимость:** Полученные навыки необходимы для отладки сетевых приложений, пентеста и защиты информации, позволяя явно видеть, какие данные «утекают» в сеть.
